Vision, core interaction model, feature pillars, and product surface areas that define CasualCrave's competitive moat.

Five Product Pillars

Mood Engine

AI-driven mood interpretation. Maps unstructured emotional input to structured intent with category, urgency, budget, and group-size signals.

Discovery Engine

Geo-aware recommendation ranking. Combines embeddings, real-time signals, and collaborative filtering to surface the highest-relevance experience.

Plan Builder

Multi-stop itinerary generator. Sequences experiences based on time, proximity, and category logic into a coherent real-world plan.

Craving Feed

Social discovery layer. Real-time activity stream showing what people around you are craving and experiencing. Core viral loop.

City Pulse

Aggregated trend surface. Shows what a city is craving in real time — enabling hyperlocal marketing and business intelligence.

Business Layer

Merchant dashboard, promoted listings, analytics. B2B surface that turns the discovery network into direct revenue.

Competitive Moat

CasualCrave's defensibility comes from three compounding advantages that get stronger with scale:

Behavioral Data Flywheel

Every mood input, click, visit, and share trains the recommendation model. No competitor can replicate a trained mood→experience corpus without the users to generate it. The model gets meaningfully better past 100k MAU.

Social Graph Lock-in

The Craving Feed creates follow relationships and social proof loops. Switching cost increases as your social graph deepens — identical to early Instagram mechanics applied to local discovery.

Local Network Density

Discovery quality in any given city is a function of how many users AND businesses are on the platform. Density creates geo-specific moats that are extremely expensive for global platforms to replicate city by city.

Mood Taxonomy IP

The proprietary mood taxonomy, intent mapping, and vector space for experience categories becomes an increasingly sophisticated knowledge graph that is difficult to replicate through traditional keyword search.

System Architecture
Microservices decomposition, data flow, event bus design, and service boundaries for a horizontally scalable platform.

Service Decomposition

CasualCrave is a domain-driven microservices architecture with clear bounded contexts. Each service owns its data, exposes a versioned API, and communicates asynchronously via event bus for non-critical paths.

API Gateway

Kong or AWS API Gateway. Rate limiting, auth passthrough (JWT validation), request routing, response caching. Single entry point for all clients.

Auth Service

JWT + refresh token issuing. OAuth2 social login (Google, Apple). Phone OTP for African markets. Stateless, horizontally scalable.

Mood Service

Accepts raw mood input. Calls AI Interpretation Service, returns structured MoodIntent object. Stores craving history per user.

AI Interpretation Service

Python FastAPI service wrapping OpenAI + custom fine-tuned classifier. Converts freeform text to MoodIntent schema. Own scaling pool.

Recommendation Service

Core ranking engine. Takes MoodIntent + geo context, queries vector store + Postgres, applies scoring function, returns ranked experience list.

Plan Builder Service

Takes top-N experiences from Recommendation Service, applies sequencing logic (time, distance, category), outputs Itinerary object.

Places Service

Owns the places/experiences data model. Handles ingestion from Google Places, Yelp, OSM. Manages enrichment, deduplication, embedding generation.

Feed Service

Craving Feed fanout. Redis-backed activity stream. Follows social graph to personalize feed. Powers City Pulse aggregation.

Notification Service

Push (FCM/APNs), email, SMS. Event-driven via Kafka. Smart batching to avoid notification fatigue. Time-of-day aware delivery.

Hybrid Scoring Architecture

The engine is a two-stage retrieve-and-rank pipeline. Stage 1 retrieves a broad candidate set using fast geo + embedding search. Stage 2 applies a weighted multi-signal scoring function to produce the final ranked list.

Scoring Function

TypeScript — Composite Score Calculation
interface ScoringSignals {
  moodRelevance:    number;  // 0–1, cosine similarity mood↔place embedding
  distance:         number;  // 0–1, inverse normalized (closer = higher)
  rating:           number;  // 0–1, normalized from 0–5 stars
  popularityScore:  number;  // 0–1, log-normalized check-in count
  trendingSignal:   number;  // 0–1, recent 24h craving velocity
  personalAffinity: number;  // 0–1, collaborative filter score (0 for new users)
  timeRelevance:    number;  // 0–1, is_open_now × hour-of-day appropriateness
}

// Weights tuned via A/B testing. Sum = 1.0
const WEIGHTS = {
  moodRelevance:    0.30,  // Highest — core product promise
  distance:         0.20,  // Critical for real-world utility
  rating:           0.15,  // Trust signal
  popularityScore:  0.10,
  trendingSignal:   0.10,  // Real-time city pulse integration
  personalAffinity: 0.10,  // Grows with user history
  timeRelevance:    0.05,
};

function computeScore(signals: ScoringSignals): number {
  return Object.entries(WEIGHTS).reduce((sum, [key, weight]) => {
    return sum + (signals[key] * weight);
  }, 0);
}

// Promoted listings: inject at positions 1, 4, 7 with score floor 0.5
// (never shown if organic score > promoted score)

Embedding Strategy

Every place and every mood are represented in the same 1536-dimensional vector space using OpenAI's text-embedding-ada-002. The embedding input for a place is a structured prompt that captures its identity:

Place Embedding Prompt Template
// Input to embedding model for each place
const buildPlaceEmbeddingText = (place: Place): string => `
  Name: ${place.name}
  Categories: ${place.categories.join(', ')}
  Mood tags: ${place.mood_tags.join(', ')}
  Price level: ${place.price_level}/4
  Description: ${place.description}

  Hours context: ${place.hours_description}
`;

// Mood embedding uses the processed MoodIntent, not raw text
const buildMoodEmbeddingText = (intent: MoodIntent): string => `
  Mood: ${intent.primary_mood}

  Atmosphere: ${intent.atmosphere}
  Budget: ${intent.budget_label}
  Group size: ${intent.group_size}
  Time context: ${intent.time_context}
`;

Cold Start Handling

New User (0 cravings)

personalAffinity = 0. Fall back to city-level trending + high-rating places. Onboarding questionnaire captures 3 preference signals to bootstrap collaborative filter.

New Place (0 cravings)

popularityScore uses global prior = 0.5. Embedding still works immediately. Boosted 20% for first 30 days to seed initial discovery and gather signal.

New City (sparse data)

Fall back to Google Places + Yelp ratings. City Pulse aggregation disabled until 500+ daily cravings. Cross-city collaborative signals used as proxy.

Diversity Reranking (MMR)

Maximal Marginal Relevance — Prevents Category Collapse
// After scoring, apply MMR to ensure result diversity
// Prevents showing 10 Italian restaurants when user said "date night"
function mmrRerank(
  candidates: ScoredPlace[],
  lambda: number = 0.7,  // 0=max diversity, 1=max relevance
  topK: number = 20
): ScoredPlace[] {
  const selected: ScoredPlace[] = [];
  const remaining = [...candidates];

  while (selected.length < topK && remaining.length > 0) {
    const best = remaining.reduce((best, candidate) => {
      const relevance = candidate.score;
      const maxSimilarity = selected.length
        ? Math.max(...selected.map(s => categorySimilarity(s, candidate)))
        : 0;
      const mmrScore = lambda * relevance - (1 - lambda) * maxSimilarity;
      return mmrScore > best.mmrScore ? { candidate, mmrScore } : best;
    }, { candidate: remaining[0], mmrScore: -Infinity });

    selected.push(best.candidate);
    remaining.splice(remaining.indexOf(best.candidate), 1);
  }
  return selected;
}

Mood Taxonomy (L1/L2 Hierarchy)

Energy States

bored, restless, energetic, adventurous, spontaneous → maps to: nightlife, activities, events, outdoor

Social Context

date night, friends hangout, solo time, family outing, group celebration → drives group_size, atmosphere

Appetite States

hungry, craving [specific food], thirsty, brunch mood, late-night bites → food, drinks, cafe

Vibe States

chill, cozy, romantic, hype, aesthetic, lowkey → atmosphere signal, filters out mismatched venues

Constraint States

broke, cheap, budget-friendly, near me, quick, close → budget_level, distance weighting

Discovery States

something new, hidden gem, trending, what's hot tonight → trendingSignal boost, exploration mode

Latency Optimization

Target: p95 < 500ms end-to-end for mood interpretation + top recommendations

LLM calls are the bottleneck. Mitigation: (1) Cache identical/near-identical inputs using input embedding similarity — if cosine distance to cached key < 0.05, return cached MoodIntent. (2) Pre-compute embeddings for the 50 most common mood templates. (3) Stream the recommendation response while LLM is still resolving for perceived speed.

Python — Semantic Cache Layer
async def interpret_mood_with_cache(raw_input: str, context: dict) -> MoodIntent:
  input_embedding = await get_embedding(raw_input)

  # Check Redis semantic cache (recent 1000 embeddings per city, TTL 15min)
  cached = await semantic_cache.find_nearest(
    embedding=input_embedding,
    threshold=0.05,    # cosine distance
    city_id=context['city_id'],
    time_bucket=get_hour_bucket()  # same hour only
  )

  if cached:
    metrics.increment('mood_cache.hit')
    return cached.intent

  # Cache miss → call LLM
  intent = await call_openai(raw_input, context)
  await semantic_cache.store(input_embedding, intent, context['city_id'])
  return intent

Infrastructure & Scaling
AWS-native deployment, caching layers, geo-distributed architecture, and cost-efficient scaling strategy from 0 to 10M+ users.

AWS Architecture (Production)

Compute

ECS Fargate for all NestJS services. Auto-scaling on CPU + request latency. No EC2 management. AI service on ECS with higher CPU allocation (4 vCPU / 8GB).

Database

RDS Aurora PostgreSQL (Multi-AZ). pgvector extension for embeddings. Read replicas in each active region. Global write, local reads.

Cache

ElastiCache Redis Cluster (6 nodes). Feed fanout, recommendation cache (5min TTL), session store, distributed rate limiting.

CDN

CloudFront for all static assets + place photos. Edge caching for /city-pulse and /places/search with location-aware cache keys. 30s TTL on trend data.

Event Bus

Amazon MSK (Managed Kafka). Topics: craving.created, checkin.completed, plan.shared, review.posted. 7-day retention.

Search

Amazon OpenSearch for full-text place search. Synced from Postgres via Debezium CDC pipeline. Geo-filtered queries <50ms p95.

Storage

S3 for photos, user avatars, plan OG images. CloudFront in front. Lifecycle: compress originals to WebP, generate 3 sizes on upload via Lambda.

Analytics

ClickHouse Cloud for City Pulse aggregation. Kafka→ClickHouse ingest via Kafka table engine. Sub-second aggregation queries over billions of events.

Monitoring

DataDog APM on all services. Custom dashboards: recommendation quality (CTR, conversion), mood cache hit rate, p95 latency per endpoint.

Geo Query Strategy

PostGIS — Efficient Geo Search
-- Stage 1: Bounding box filter (FAST, uses index)
-- Then exact distance filter. Then embedding ANN. Never reverse.

SELECT p.id, p.name, p.crave_score, p.embedding,
  ST_Distance(p.location::geography, ST_MakePoint(7.4898, 9.0820)::geography) AS dist_m
FROM places p
WHERE
  p.city_id = '$city_id'
  AND p.is_open_now = true
  AND p.mood_tags && ARRAY['romantic', 'dinner']       -- GIN index
  AND ST_DWithin(                                         -- GIST index hit
    p.location::geography,
    ST_MakePoint(7.4898, 9.0820)::geography,
    5000                                                   -- 5km radius
  )
ORDER BY p.crave_score DESC
LIMIT 200;                                               -- Stage 1 candidates

-- Stage 2: Vector similarity applied IN APPLICATION LAYER
-- (cheaper to filter 200 candidates in app than do ANN on all 50k city places)

Launch City Strategy

Launch in 1 city, dominate it before expanding.

Abuja as launch city. Target density: 500+ places, 5,000+ users within 90 days. City Pulse only unlocks at 500 daily cravings — use this as the "city is alive" threshold that justifies expansion to Lagos, then Nairobi, then London/Toronto diaspora markets. Playbook documented and repeatable per city.

Growth Strategy
Viral loops, social mechanics, and acquisition channels engineered into the core product experience.

Core Viral Loops

Loop 1 — Plan Share

User generates a plan → shares on WhatsApp/X/Instagram Story → recipient sees a beautifully designed plan page → downloads app to create their own. One of the highest-converting cold acquisition loops because the shared content is genuinely useful, not just promotional.

Loop 2 — Craving Feed

User follows friends → sees their cravings → gets inspired → creates their own craving → appears in followers' feeds. Classic social graph growth loop. Identical to how Twitter/Strava drives habitual use through social proof and FOMO signals.

Loop 3 — Business Referral

Venue gets tagged in cravings + check-ins → venue owner sees organic traffic → signs up for merchant account → promotes listing → more visibility → more user cravings → more venue sign-ups. B2B2C flywheel that funds user growth.

Loop 4 — City Pulse

City Pulse is publicly accessible (no login) and embeddable. Media outlets, blogs, and influencers share "What Abuja is craving tonight." Each share drives brand awareness and app installs from people who want to influence or join the pulse.

Retention Mechanics

Weekly City Pulse Digest

Push notification every Friday: "Here's what Abuja is craving this weekend." Personalized based on user's top categories. High open rate because it's genuinely timely.

Craving Streak

Gamified streak for consecutive weeks with a craving. Small but effective — Duolingo proved the mechanic at scale. Shown on profile as social signal.

Plan History

"1 year ago you craved..." memory feature. Emotional hook. Drives re-engagement from dormant users and encourages re-visiting favourite spots.

Section 10
Monetization Model
Multi-layered revenue architecture designed to align platform incentives with user value and scale to $10M+ ARR.

Revenue Streams

Promoted Listings

Venues bid to appear in recommendation results for specific moods. CPM-based auction. Mood-targeted ads are 3–5× more relevant than location-only targeting — premium CPM justified. Target: ₦5,000–50,000/day per listing.

CravePass (Subscriptions)

Monthly subscription unlocking: early access to trending spots, premium plan features (5-stop itineraries), exclusive group deals, ad-free experience. Price: ~$3–5/month. Target 5% conversion of active users.

Booking Commissions

10–15% commission on reservations, tickets, and group deals booked through platform. Requires venue integration API. High value per transaction — one group dinner = $20–50 commission. Phase 3 revenue.

City Intelligence

B2B SaaS: sell aggregated craving trend data to city councils, tourism boards, real estate developers, and retail chains deciding where to open next location. Monthly data subscription. $500–5,000/month per client.

Group Deals

Venues offer exclusive deals to groups of 4+ users. CasualCrave takes 10–20% margin. Drives group use cases — the highest LTV user segment. Venue wins with guaranteed table fills, platform wins on margin.

Gifting

Send a "Crave Gift" — a curated experience recommendation sent to a friend with a message. Venue earns the sale, platform earns a fee. Gift cards + gifted itineraries. Holiday/birthday use case.

Strategic Note on African Market Pricing

Price in local currency (NGN, KES, GHS) and keep friction near zero. The willingness to pay exists — users spend $50+ on a night out but baulk at $1/month subscriptions if the payment flow is broken. Integrate Paystack and Flutterwave from day one. USSD fallback for low-connectivity markets. The infrastructure investment in African payment rails is itself a competitive moat vs. global platforms that treat it as an afterthought.
